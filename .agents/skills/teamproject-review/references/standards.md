# 评审与完成定义规范

以下规范用于判断单条变更是否可合并、可交付；完成结论以当前提交的场景覆盖与验证证据为依据。

| 规范项 | 本项目的执行要求 | 检查与验收方式 |
| :--- | :--- | :--- |
| REV-01 完成定义（Definition of Done） | 变更完成须同时满足：约定场景及失败/边界处理全部实现、适用用例通过、门禁通过、评审问题关闭、相关文档同步、验证记录归档。涉及权限、迁移、模型或发布的变更还须提供对应验证。涉及可选功能时注明适用范围，并验证关闭该功能时个人主流程仍可用。其他不适用项说明原因。纯文档变更按内容一致性、链接及格式检查验收，不机械新增业务测试。 | 在变更记录逐项勾选并链接证据；未满足项不得标记完成，任务代码写完不能代替完整验收。 |
| REV-02 变更规模上限 | 一次变更只覆盖一组可独立验收的相关任务，手工维护文件原则上不超过 15 个；无关重构、格式化与功能修改分开。超过上限优先拆分；无法安全拆开的原子迁移等按例外流程登记。锁文件及生成文件单独列出，不计入手工文件数，但仍检查来源和影响。 | 对照任务组、文件清单与差异；超限且没有必要性说明及例外记录的变更退回拆分。 |
| REV-03 评审检查表 | 人工评审检查场景与业务结果、逐资源授权、事务及迁移恢复、AI 人工确认边界和提示词评测；Harness（自动化规范检查）检查分层、命名、契约、测试与文档登记等一致性，不能代替业务判断；格式与代码风格交给格式化和静态检查工具。按实际改动勾选适用项。 | 评审记录明确三类检查各自结果，涉及模型变更有评测报告，涉及迁移有回滚或恢复证据；不能只留一句“已检查”。 |
| REV-04 责任人与时限 | 每条变更指定提交人、评审人及批准人；批准人由项目维护者担任或明确授权，提交人不能自行关闭未获认可的评审意见。评审请求发出后 1 个工作日内首次响应，原则上 2 个工作日内给出结论或剩余问题与预计时间；超时提醒维护者重新分派，不按默认同意处理。单人开发时由项目负责人完成最终确认并留记录。 | 抽查责任人、请求时间、响应及结论；超期请求有提醒或重新分派记录，批准前不得宣称已获通过。 |
| REV-05 门禁必跑 | 合并前对待合并的最新提交运行 README 登记的统一门禁命令，包含适用的格式/静态检查、测试、安全扫描及文档检查；模型相关变更另关联评测结果。统一入口尚未建立时，纯规范文档变更记录实际执行的结构、内容和链接检查，并标明统一门禁未执行。业务变更建立对应的可重放检查并说明适用范围。不得跳过本地钩子、忽略失败或放宽检查让结果变绿；提交再次改动后重跑受影响门禁及统一入口。 | 合并记录可对应提交号、执行命令、退出码与报告；旧提交的绿色结果不能作为新提交的通过依据。 |
| REV-06 例外书面化 | 确需保留旧写法或暂缓某项要求时，在本文的例外条目登记范围、理由、风险、替代控制、责任人、批准人及到期日，并关联变更；会话讨论须落入记录后才形成项目例外。例外不能覆盖权限隔离、机密保护等底线，也不能把实际失败标记为通过；到期应整改或重新评估，不永久忽略。 | 按变更查找有效例外，缺范围、批准或到期信息即无效；检查过期项已整改或重新评估。 |
| REV-07 证据归档 | 在 docs/changes/<变更名>/ 集中归档变更说明、验证记录、评审结论，可分为三份文件或一份文件的三个明确章节；记录场景、提交号、命令、环境、结果及相关报告路径，避免复制敏感数据。既有 docs/releases/ 发布记录与模型评测报告通过链接关联，不重复维护冲突结论。 | 按变更名一次找到三类材料，证据可对应实际提交；仅有无日志支撑的“全部通过”不算验证记录。 |
| REV-08 复盘留痕 | 门禁失败、线上故障和实质性返工在变更说明或决策记录中写明触发条件、原因、影响、修复和预防措施；补充必要回归用例或更新规范，并指定后续任务负责人。记录最终方案及重要取舍，不把临时尝试逐条堆成流水账。 | 抽查失败与返工能否检索到原因、处置和后续验证；同类问题复发时可追溯此前措施是否落实。 |
